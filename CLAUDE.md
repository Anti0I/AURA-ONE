# AURA ONE

A product page for hardware that does not exist, built as a portfolio piece
about scroll-driven canvas rendering, procedural asset generation and
memory discipline.

**The founding constraint: every asset is generated from code.** No stock
photography, no purchased 3D model, no HDRI, no texture files, no audio files,
no paid API keys — for the author or for anyone opening the page. If a change
would introduce a binary asset that cannot be regenerated by
`npm run assets:all`, that is a design decision worth stopping to discuss, not a
detail.

Long-form reasoning lives at `src/app/engineering/page.tsx`, rendered for
visitors at `/engineering`. `README.md` is the contributor-facing version. This
file is the working knowledge that is expensive to re-derive.

---

## Commands

```bash
npm run dev              # Next 16 dev server, Turbopack
npm run verify           # typecheck + lint + 32 unit tests — run before every commit
npm run build            # production build
npm run audit:budget     # asset + JS budget gate; needs a build first
npm run test:e2e         # 52 Playwright tests, desktop + mobile projects (~7 min)
npm run test:a11y        # 10 axe / keyboard / reduced-motion tests
npm run test:perf        # scrub continuity, own config, one worker (~30 s)
npm run assets:all       # regenerate every asset from primitives (~4 min; needs ffmpeg)
node scripts/shoot.mjs   # screenshot the stage at five scroll positions
```

All three Playwright suites reuse a running server when there is one and
otherwise build and start their own, and all three need `public/seq/` to exist —
it is committed, so a fresh clone works without a render.

`test:perf` has its own config (`playwright.perf.config.ts`) at one worker. It
drives the page with `?debug=1`, which is the only thing that puts the live
telemetry object on `window`; a normal visit pays one string comparison at boot
and gets nothing else.

## Hard rules

These are the ones that cause silent breakage rather than an error.

1. **Nothing that changes per frame goes through React state.** Per-frame values
   are written straight to `style` on refs, or to the mutable `telemetry` object
   in `src/store/transient.ts`. A full scrub of the stage causes zero
   re-renders; keep it that way. Zustand is for discrete state only — the
   material and the story phase (which changes three times in
   total).

2. **There is exactly one animation loop**, `src/lib/scroll/rafBus.ts`. Never
   call `requestAnimationFrame` directly. Subscribers run in ascending priority:
   `INPUT` (0) may read layout, `RENDER` (100) may only write, `MEASURE` (200)
   observes the finished frame. Reading layout after a write in the same frame
   forces a synchronous reflow.

3. **`ImageBitmap` must be `close()`d.** Its memory lives outside the JS heap and
   GC will not reclaim it. `BitmapLRU` owns this; the unit tests assert on
   `close()` calls rather than on cache size, because skipping the call still
   *works* — it just leaks until the tab dies.

4. **Frames decode to the size they will be drawn**, not the size they were
   encoded. A bitmap costs the same whether or not the detail is visible.

5. **The shell renders neutral grey in the baked frames.** The walkthrough is
   a frame sequence, so a colour baked into the render means re-rendering all
   240 per variant. The live configurator overrides it through
   `setFinish`; the no-WebGL fallback composites it at draw time.

   And: **the two frame sources must stay interchangeable.** `video.worker.ts`
   and `decoder.worker.ts` speak one protocol and both return `ImageBitmap`s
   at drawn size. Anything that makes the player branch on which is running has
   put the abstraction back where it started.

6. **Anything that animates on a loop is gated on visibility.** Use
   `onFrameWhileVisible` from `src/lib/scroll/onScreen.ts`, never `onFrame`
   directly, for anything with no natural end — an idle spin, a sweep, a
   damped playhead. This has been the same bug four times. Measured parked at
   the footer with every section mounted and none visible: 720 `clearRect`
   and 720 `getBoundingClientRect` in three seconds, against 0 after.

7. **New below-the-fold sections are code-split.** Client wrapper +
   `next/dynamic({ ssr: false })` + `LazySection`, following
   `src/components/xray/XraySectionLazy.tsx`. Pass `LazySection` the section's
   `id` so the anchor exists before the section mounts.

8. **Numbers appear in one place.** The spec table and the encoder-written
   manifest are what the page and the engineering notes read. Nothing on this
   site may quote a frame count, a file size or a figure the build disagrees
   with — a spec sheet contradicting the paragraph beside it is the worst
   failure this project can have.

## Traps

Each of these cost real time. They are all still live.

**Canvas drawing is deferred, so the profile blames the wrong line.** A 2D
canvas queues its paint calls and replays them on first use. If that first use
is `getImageData`, the whole bill — replay plus a synchronous readback off the
GPU — lands on the read. Timing the sections of `pcbTextures` put 4514 ms of a
4604 ms run inside the Sobel pass and ~3 ms in all the drawing, which is a lie
in both directions. Two things follow. Any canvas that will be read back must
be created with `getContext("2d", { willReadFrequently: true })` — that one
argument took the board from 4604 ms to 58 ms. And to attribute cost inside a
generator you have to force a flush at each mark, or you are timing when the
queue happened to drain.

**`use` is a React hook, even in a file with no React in it.** Naming a local
helper `use()` makes `react-hooks/rules-of-hooks` fire on every call site:
fifty-three errors from `assets-src/device/textures.mjs`, which is a plain ESM
module rendered in headless Chromium. The helper is called `paint()`.

**Emissive is not lighting.** An `emissiveMap` is self-lit: it ignores every
light in the scene, takes no shading across a form, throws no specular and
casts no sense of depth. Every internal part used to be a flat base colour with
its whole texture on `emissiveMap`, which is exactly why they read as decals
stuck to primitives. A texture only becomes a surface once it feeds `map`,
`roughnessMap`, `metalnessMap` and `normalMap`. Emissive still has a job here —
the X-Ray pose and the push-in lift it to keep the internals legible through
the shell — but as a stylisation *on top of* a lit surface, at a twentieth of
its former strength.

**`tailwind-merge` and the custom type scale.** It assumes any unrecognised
`text-*` class is a colour, so `text-display text-ink` reads as a conflict and
the font size is silently dropped — a headline at 16px with no error anywhere.
`cn()` in `src/lib/utils.ts` registers the scale. Any new `@theme` key sharing a
prefix with a built-in group needs the same treatment.

**`globalCompositeOperation: "color"` cannot darken.** It takes hue and
saturation from the source and *luminosity from the backdrop*. Filling a bright
chrome render with near-black gives bright chrome and an invisible hue shift.
Lightness comes from `Material.exposure`, authored from the OKLab lightness of
the tint. See `src/lib/canvas/tint.ts`.

**Assigning to `canvas.width` resets the whole 2D context state.** Smoothing,
alpha, transform, composite mode — all of it, every time, including when you
assign the same value it already had. Anything configured once in a constructor
survives exactly until the first resize, and the first resize happens during
boot. `imageSmoothingQuality` is re-applied inside `resize()` for that reason,
and it is not decoration: the master is 1440 square and a 1440p panel at dpr 2
draws the artwork at 2477 device pixels, so an upsampling filter runs on every
frame whether or not anyone chose one.

**The decode size quantises with `ceil`, and both halves of that matter.** It
keeps the decode at or above the drawn size so the 2D canvas only ever scales
*down*, and it holds the whole hero-to-story framing sweep inside a single
160px step — at dpr 1 on a 1080p panel the drawn square runs 817 to 929 px, and
`ceil` calls both of those 960 where `round` would call them 800 and 960 and
invalidate the entire cache halfway through the opening animation.

**A frame count is not a memory budget.** The same 24 frames are 39 MB decoded
at 640² and 199 MB at 1440². `BitmapLRU` takes both a count and a byte ceiling.

**A `VideoFrame` pins a decoder buffer**, the same way an `ImageBitmap` pins
heap-external memory. `onFrame` closes in a `finally` on every path,
including the ones that return early — hold a handful and the decoder stalls
waiting on its own pool, silently.

**The video scheduler needs to know what is already in flight.** Without it,
"you asked for that and it is coming" is indistinguishable from "that is behind
the head, rewind", and it picks the second. The first version reset the decoder
on every network chunk and produced not one frame, without ever erroring —
resetting a decoder is perfectly legal. `inFlight` in `video.worker.ts` is
that distinction.

**A decoder's queue is latency, not buffer.** It is a FIFO: a frame requested
now comes out after everything already queued has. Depth measured in frames
hides that completely — twenty-four frames is 40 ms of latency where a
composite costs 1.65 ms and 900 ms where it costs 38, and both are real
machines. The depth is derived from the measured composite cost
(`TARGET_QUEUE_MS`), not chosen.

**Never rewind while the sweep still has work ahead of it.** The decode head is
deliberately ahead of the playhead, so the frame on screen is usually *behind*
the head, and chasing it means `reset()` — which drops everything in flight.
Then the playhead moves and it happens again. Measured as half a second in
which the decoder ran flat out and delivered three frames. `pickTarget` takes
anything ahead first and only rewinds when the sweep has genuinely run out.

**A request has to aim where the playhead is going.** A frame asked for at N
arrives `latency` later, by which point the scroll is at N + speed x latency —
sixty frames on a software rasteriser against a `nearest()` search range of
twelve, so the canvas had nothing to show and froze. The player measures
round-trip time as a *time*, not as a distance in frames: a distance is only
true at one scroll speed, so it has to be relearnt exactly when it is needed
and has not converged. A time is a property of the machine, learnt during
ordinary scrolling and already right when a flick starts.

**`nearest()` is asymmetric about the direction of travel**, not about the
index. Against the travel it covers the measured lag; with the travel it must
not, because the player aims ahead deliberately and the frames arriving early
are frames the scroll has not reached — a symmetric search showed frame 220
while the playhead was at 162. Which side counts as "stale" flips when the
scroll reverses, and hard-coding it towards lower indices was right going down
the page and exactly backwards coming up.

**Scrolling back up is the expensive direction.** A frame decodes only from the
keyframe at or before it, so a reverse scrub asks for a descending ladder with
every rung behind the decode head. Serving the nearest rung first leaves the
next one behind the *new* head as well, and every frame costs its own reset:
`pickTarget` goes to the bottom of the ladder instead, which turns the whole
ladder into one rewind and one forward sweep. Frames then arrive in the opposite
order to the one the playhead wants, which does not matter — they land in the
cache either way. Removing this took the largest gap from 128–144 to 42–80.

**postMessage is FIFO, so a window sent after the requests it authorises loses
them.** The worker measures each request against the window it had a tick ago
and silently drops the ones that have just come into range; the player counts
those as outstanding and never re-asks. Measured as the playhead sitting on
frame 163 with the canvas showing 149 and 27 requests pending, permanently.
`prefetch` announces first, then asks.

**A `subarray` pins the buffer it was cut from.** `IvfReader` used to
concatenate each network chunk onto a growing accumulator and hand out views
into it, so every frame kept its whole accumulator alive — 181 MB retained and
359 MB copied for a 3.87 MB stream, on the worker thread, during the hero. It
now copies each frame once into a buffer of its own size. Its queue uses a head
pointer rather than `shift()`: shifting is O(n) in queue length and the queue
is longest exactly when the chunks are smallest.

**A guarded cache window bigger than the byte ceiling makes the ceiling
decorative.** `BitmapLRU` used to stop evicting once everything left was
guarded, so at 1440² — 7.91 MB a frame, 29 in the window — it sat at 189.8 MB
against a stated 160. The guard still beats the *count* limit and no longer
beats the byte limit, and the player sizes its window from what the budget
affords.

**`background-position` is not a compositable property**, and neither is
anything else you might reach for to move a texture. Animating it repaints the
element every step; `will-change: background-position` only gives it a layer to
repaint in. `mix-blend-mode` is worse in a different way — it forces the
compositor to read the backdrop, and the grain sits directly over the stage
canvas. Move an oversized child by `transform` instead, and compensate the
overhang in `background-position` or the tile lands on different pixels.

**What breaks `position: sticky` is `overflow`, and only `overflow`.**
Measured in the target browser rather than assumed, because this entry
previously claimed `filter` was the culprit and that is simply false:

    plain (control)            STICKS
    filter: blur()             STICKS
    will-change: transform     STICKS
    transform: translateZ(0)   STICKS
    contain: paint             STICKS
    overflow: hidden           BROKEN
    overflow-x: hidden         BROKEN
    overflow: clip             STICKS

`transform`, `filter` and `will-change` create a containing block for *fixed*
descendants — sticky is not fixed, and it positions against the nearest
scrollport. `overflow: hidden` makes an ancestor into that scrollport, which is
why it is the one that bites; `overflow-x: hidden` bites for the same reason,
because it computes `overflow-y` to `auto`. `overflow: clip` does not create a
scroll container and is the safe way to clip around something pinned.

Both pinned sections put `overflow-hidden` on the sticky element *itself*, which
is fine — it is ancestors that matter.

**A translucent layer over a canvas costs by area, every frame.** The most
expensive thing in the acoustics stage turned out to be one nobody suspected.
An element with an opacity below 1 is a group the compositor has to blend
against whatever is behind it, and behind these cards is a canvas repainting
sixty times a second — so the bill follows the card's *area*, which is exactly
what an approach increases. Interleaved against a control that scrolls the same
section through the gap where no card is moving:

    translucent throughout   19.90 ms/frame, 24 long   (control 16.69, 1)
    opaque throughout        16.62 ms/frame,  0 long   (control 16.60, 0)

So the dimming belongs to the parking spot, not to the journey: the fade lifts
to fully opaque over the first eighth of an approach, and the card travels the
rest of the way free. It is the better picture as well — the field showing
through is depth when a card is small and clutter under a paragraph.

**Beware which measurement you take.** The two entries above were nearly
recorded the wrong way round. Frame times sampled with the scroll *parked* said
this section cost nothing, and could not have said anything else: blending and
re-rasterisation only happen while something is changing. The number that
mattered came from sampling while scrolling at a fixed rate, against another
scroll at the same rate through a part of the section where nothing scales —
and A/B interleaved in one session, because the machine drifts by more than the
effect between runs.

**A scale change re-rasterises a layer; a rotation or a translation does not.**
True, and it is why a parked card varies only its three rotations while its
scale, depth and position stay frozen — three text cards breathing at rest
would be a cost with no end. But it was *not* what made the approach expensive:
stepping the scale to cut rasterisations, tried first on exactly this
suspicion, moved the figure from 19.90 ms to 19.90 ms. The step was removed
again rather than kept as machinery that earns nothing.

**`opacity` and `transform-style: preserve-3d` cannot share an element.**
Opacity is a grouping property, and a grouping property computes
`transform-style` back to `flat` — which silently collapses a card's front and
back faces into the same plane, so the flip shows both at once and neither
`backface-visibility` nor the z-order helps. The acoustics cards put the
transform and the 3D context on one element and the fade on the faces inside
it. There is no warning for this; the card simply stops being a card.

**Two beats of the same story must never share a *readable* window.** The
acoustics section used to run beat N's exit and beat N+1's entrance over exactly
the same stretch of scroll. That is about 36svh — a dozen wheel notches — in
which half of one paragraph sits above half of the next and neither can be read,
and scrolling slowly lands in it every single time. It was reported as "the text
goes weird", which is what a reader has to call it.

The word *readable* is doing work. All three beats are now on screen at once,
parked in the scene, and that is fine: at a third of full size, faded to 0.46,
with everything except the number and the title at zero opacity, they are
scenery. What must never be true is two of them carrying body copy anybody
could try to read. `stations.ts` keeps the windows disjoint, and
`tests/e2e/acoustics.spec.ts` measures the *composed* opacity of every beat's
paragraph at fifteen scroll positions rather than trusting that the fades follow
the arithmetic.

Note that this is the **opposite** of the rule two entries below about section
hand-off, and the difference is what is dissolving. Two backgrounds crossing
read as one place becoming another. Two paragraphs crossing read as a fault.
The gap the disjoint windows leave has to be given something to do — the
starfield runs at its fastest there, and the cards visibly turn in their parking
spots. If a gap like that has nothing to do, the transition is wrong rather than
the gap.

Three traps that used to live here went with the wipe, because with one beat
moving at a time there are no clipping windows left to fall into: percentage
translations resolving against the mover rather than the clip, unequal beats
crossing at an offset because each was centred independently, and focus rings
being eaten by an `overflow: hidden` mask. The last of those is still a rule
worth keeping in mind anywhere else — **a clipped focus ring is the only
feedback a keyboard user has about where they are** — it just no longer has a
call site here.

**A blur radius has to be quantised.** `opacity` and `transform` are compositor
properties and cost nothing per frame; `filter: blur()` re-rasterises the layer
at layer size on every distinct radius. `SectionHandoff` steps the radius so a
whole transition costs four or five rasterisations rather than one per frame,
which is the same answer `.noise-field` reached with `steps(8)`. And at the ends
the filter is *removed*, not set to `blur(0px)` — a zero radius still promotes
the element and still runs the pass.

**An entrance and an exit across one boundary must be complements.** For
adjacent sections the incoming top edge and the outgoing bottom edge are the
same edge, so thresholds measured from the viewport top make `enter + exit`
sum to exactly 1 and the boundary cross-dissolves. Measuring each from the
nearest viewport edge instead looks equivalent and is not: measured across the
boundary, the incoming section was fully arrived before the outgoing one had
begun to leave.

**Nothing may construct the AudioContext except a request for sound.** Interface
voices — a hover tick, a scanner lock — used to call `ensureAudio()`, so merely
scrolling past the scanner built an audio graph and a device handle. Nothing was
audible, and that is exactly why it survived for so long: a whole audio system
created for silence, on a page that promises it stays off until asked.

The voices are gone now along with the sound switch, so the rule has become
structural rather than a discipline to remember: the only caller of
`ensureAudio()` is `playDemo`, and the only caller of that is a click on Play.
If a second one ever appears, it has to answer why a visitor asked for it.

**A role-name regex is a substring match, not a name match.** `{ name: /Sound/ }`
matched the audio toggle until the acoustics section added "Play — Sound keeps
its address.", and then failed as a strict-mode violation in two suites at once.
The toggle is gone; the trap is not. Anchor these patterns at both ends.

**`perl -0pi -e` will interpolate `$` and backticks in the replacement.** This
file was duplicated end to end by one, because a replacement ending in an
anchored-regex example contained a dollar sign immediately before a backtick —
which Perl reads as `$PREMATCH`, and dutifully pasted every preceding line of
the file back into itself. Use the Write tool for prose, or a quoted heredoc;
this is the third time shell quoting has damaged a file in this repository.

**`will-change` is a promise, not a hint you can leave on.** It holds a
compositor layer for as long as it is set. The hero copy and the four captions
are full-viewport elements; clear it in the same write that sets
`visibility: hidden`.

**Lenis owns the scroll position, so tests must not jump.** A programmatic
`window.scrollTo` gets pulled back towards Lenis's own target, and a test that
jumps is measuring somewhere other than where it thinks it is. That produced a
very convincing screenshot of the wrong frame. Drive with `mouse.wheel`, and
converge rather than aiming once — the inertial tail overshoots a single
impulse.

**The e2e suite runs two workers on purpose.** Each one decodes a 2896x1440 VP9
stream or renders three.js through software WebGL while reading pixels back. One
worker per core starves them, and starvation looks exactly like the regressions
the tests exist to catch.

**A performance test must not share the machine.** `tests/perf` has its own
config at one worker for that reason: run beside the rest of the suite it
reported a largest gap of 169, where alone it reports 42 to 80 on the desktop
stream and 21 to 28 on the mobile one. For the same reason it asserts on the
fraction of the playhead's journey the picture covered — the one figure here
that does not simply get worse on a slower machine — and merely *logs*
granularity, which does.

**Headless Chromium composites in software, and it is 300x slower.** WebGL in
the worker runs on SwiftShader: the packed-frame texture upload costs 32 ms
there against 0.1 ms on a discrete GPU. Profiling headless and optimising for
what you find is optimising for a machine nobody uses — check the renderer
string before believing a number. It cuts both ways: the same gap is why the
CI budgets are looser than the figures a real browser reports.

**Boot progress must be measured, not counted.** A resize bumps the decoder's
generation and the worker discards everything in flight, so counting replies
leaves the counter permanently short and the preloader never releases the page.
It only reproduces where layout settles late — every mobile test failed, desktop
never did. There is also a hard 12 s timeout, because an overlay that blocks
scrolling must always let go.

**Fixed `waitForTimeout` in canvas tests is a flake generator.** Sleeps tuned on
an idle machine fail under a parallel run. Poll for the actual state: `scrubTo`
in `tests/e2e/stage.spec.ts` waits for the frame to *change and then settle*
(waiting only for stability exits immediately, because right after a scroll the
canvas still holds the previous frame and is briefly perfectly stable).

**Satori needs explicit `display: flex`** on any element with more than one
child, and JSX makes `{X}.` two children. `src/app/opengraph-image.tsx` uses
template literals to keep text nodes single.

**ESLint blocks `setState` inside effects.** For platform capabilities that never
change, use `useClientValue` (`src/lib/useClientValue.ts`), which wraps
`useSyncExternalStore`. Never write a ref during render either — construct
lazily inside a callback instead.

**`playwright.config.ts` needs `testMatch`.** `testDir: "tests"` otherwise picks
up `tests/unit` and fails on the first vitest import. It also has to leave
`perf/**` out, or the performance suite runs two-wide with everything else and
measures the neighbours; `playwright.perf.config.ts` spreads the base config and
overrides only what runs and how much runs beside it.

## How the pieces work

**Stage.** Hero and scrollytelling share one canvas, so there is no seam to
cross-fade between "product at rest" and "product rotating". The pinned section
is `position: sticky` — there is no GSAP and no ScrollTrigger — and progress is
one `getBoundingClientRect` per frame during the INPUT phase. Camera framing is
a per-tier table of hero and story poses: desktop moves the product sideways to
make room for copy beside it, mobile moves it up because there is no beside.

**Two frame sources, one protocol.** `video.worker.ts` drives `VideoDecoder`
over a VP9 IVF stream; `decoder.worker.ts` fetches WebP stills. Both return
`ImageBitmap`s at drawn size, so the LRU, the byte budget and the draw path are
identical either way. The worker reports `unsupported` and the player swaps —
the probe is async and the answer is only needed inside the worker. Which one
won is on the canvas as `data-source`, because production strips
`window.__player` and the fallback is invisible when it works *and* when it
breaks.

**Why a video, given the whole player exists because video cannot be scrubbed.**
That is true of the `<video>` element, not of video: `currentTime` is a
request to seek, `VideoDecoder` is not. Inter-frame prediction then costs
3.87 MB where the same 240 pictures cost 9.95 MB as stills.

**Seeking.** A frame decodes only from the keyframe at or before it, so a
backwards jump costs up to one GOP (16). Frames passed on the way are
composited if they were wanted and dropped if not — one decode either way.

**Scheduling.** Everything the player does about a fast scrub comes from two
measurements it takes of itself: delivery rate, in frames per second, and
round-trip latency, in seconds. Below the delivery rate it asks for every frame
and nothing changes. Above it, the timeline is sampled at a stride that matches
what can actually arrive, and each request aims `speed x latency` frames ahead
of the playhead so the frame lands *at* the scroll rather than behind it. Both
are properties of the machine rather than constants: the same build composites
a frame in 0.1 ms on a discrete GPU and 32 ms in software, and a number chosen
for either one is wrong on the other.

The visible consequence is that a slow machine draws fewer, wider-spaced
pictures and still follows the scroll end to end. That is the figure
`tests/perf` asserts on, and it was 0.10 before this — the canvas covered
twenty-four frames while the scroll crossed two hundred and thirty-nine.

**Whole frames only.** The draw used to keep the playhead's fractional position
and cross-fade the two frames it sat between. It was removed: the walkthrough
turns 360 degrees across the 72 frames of its rotate phase — 5 degrees a frame,
PSNR 20.7 dB between neighbours — so the blend read as a double exposure rather
than as travel, with the mic holes, the indicator and the port ring visibly
doubled. Worse at rest than in motion, because `damp()` settles on an arbitrary
fraction and the ghost then stays put forever.

It was also buying nothing. At 40px wheel steps the playhead crosses about 2.8
frames, so nearly every step lands on a different frame regardless: 58 distinct
pictures across 60 steps without it, 59 with. The 87-against-48 figure it was
justified by compared the *video* against the *still* fallback, which has half
the frames — it was never a measurement of the blend.

**Format split.** VP9 for the walkthrough, WebP for its fallback, AVIF for the
two X-Ray stills. AVIF is ~18% smaller per frame but decodes ~3× slower with
alpha, and a fast scrub decodes several frames per animation frame. Bytes are
one-time; decode is per-scrub.

**Scanner.** Two renders from an identical camera, stacked, with a circular
window into the lower one. The lens is a fixed-size element that is
*translated*, and the copy of the artwork inside it is translated by exactly the
opposite amount. Animating `mask-image` or `clip-path` position recomputes the
mask on the compositor's critical path every frame.

**Section hand-off.** Sections do not abut, they dissolve into one another:
`SectionHandoff` drives opacity and scale continuously and a stepped blur
alongside them, from each section's own edges. Blur is dropped on mobile and
under reduced motion, where opacity and scale carry it alone.

**Text entrance** is `Reveal`, on the shared frame bus. There is no GSAP here
and there is not going to be: it is ~40 KB gzip against 15 KB of first-load
headroom, and it brings its own ticker into a page whose ordering guarantees
depend on there being exactly one.

**Acoustics.** The only claim on the site made in sound, and it ships no audio
bytes — a sweep, brown noise with the suppression engaging mid-clip, and a
panned orbit, all built from oscillators and filters. The meter reads an
`AnalyserNode` tapped off the demos' own output stage rather than the master,
so it reads the demonstration and nothing else. It draws its resting state once
and only subscribes to the frame loop while something is playing.

**The second pinned section.** On a wide viewport the acoustics section is
520svh with a sticky frame — the same sticky-plus-one-rect mechanism as the
walkthrough, which is the whole argument for not having taken a scroll plugin.
On a narrow viewport, and under reduced motion, it is an ordinary stacked list
instead: `AcousticsPinned` and `AcousticsFlat` are separate components because
they are genuinely different documents — one keeps a single beat in the tab
order, the other holds all three — and `useAcousticsDemo` owns everything that
is not layout.

**The stage is a 3D scene and every beat is always in it.** Each card has a
parking spot — its own corner, its own depth, its own period — where it turns
slowly on all three axes behind a `perspective: 1400px`. The scroll brings them
forward one at a time to `translate3d(0,0,0)`, dead centre, where the
perspective distortion is exactly zero and the copy is as sharp as flat type.
`stations.ts` keeps their windows disjoint, so what is parked is never
competing with what is being read: a parked card shows its number and its title
over a schematic grid and nothing else, and the grid is the inverse of the body
copy — one fades in as the other fades out, so a card with its paragraph hidden
reads as an object waiting rather than as a panel that failed to load.

The spin free-runs only while a card is parked, and the angle it will settle
flat to is latched at the same moment. Both halves matter: if the spin kept
accumulating on the way in, the nearest whole turn would flip somewhere
mid-approach and the card would snap through a half rotation.

**The approach is paced, and the curve matters as much as the length.** Coming
towards you gets roughly twice the scroll that going away does — `FADE_IN` 0.45
of a station against `FADE_OUT` 0.22, which at 520svh is about 54svh in and
26svh out. The first version gave each a fifth of a station, some 15svh, which
is a wheel notch and a half from parked to fully arrived; it was reported as
happening instantly, and it was. But lengthening the window alone would not have
fixed it: the stage ran on `easeInOutQuart`, which parks near 0 and near 1 and
crosses the middle at four times the average rate, so a scroll-driven approach
built on it reads as *nothing, snap, nothing* however much scroll it is given.
It now uses `smoothstep`, which is very nearly linear through the middle, so a
notch of wheel buys a proportional step closer.

Worth knowing before retuning: one approach is about six notches of a 100px
wheel, and buying six more costs 600px of document per beat. Thirty notches an
approach — which is what "make it gradual" sounds like in the abstract — would
put the section past a thousand svh on its own.

One number carries the whole thing. `presence` — 0 at the parking spot, 1 on the
front — drives the position, the depth, the scale, how far the tumble is allowed
to swing, how bright the card is, whether its body copy exists, how fast the
starfield behind is running, and how far the signal chain in the readout is out
of focus. There is no second timeline to keep in step, because there is only
one, and that is why the fastest part of the flight is exactly the part with
nothing to read.

That last one replaced the only hard cut left in the section. The chain follows
the rail, the rail changes over mid-flight, and three lines of monospace used to
replace themselves between two frames — which reads as a fault in something
else. It now defocuses on the way out of a station and resolves on the way into
the next, so the swap lands where `presence` is 0 and nobody can see it happen.
Driven from the scroll rather than from a timer started when the text changed:
reversible for free, and it cannot race the gesture. The radius is stepped,
because unlike a one-off transition this one is scroll-driven and every distinct
radius is another rasterisation.

The read/write split is not optional here. `onProgress` runs during INPUT and
writes only refs; a single RENDER task composes parking, approach and tumble
into one `transform` per card. It has to be a separate task, because the tumble
runs whether or not anybody is scrolling and `useSectionProgress` deliberately
says nothing when the progress has not changed — a stage driven from there alone
freezes the instant the page comes to rest. The starfield is split the same way
for the same reason, and both are gated on visibility.

**The starfield.** `lib/canvas/Starfield.ts`, on the same fixed-pool discipline
as `Particles`. Stars are projected from a depth `z` and drawn as the segment
between where each one is and where it was a moment ago — so a stationary field
is points and a scrolled one is streaks, with no switch between the two modes
and no second implementation. Speed is `cruise + boost x (1 - presence) +
gain x |dp/dt|`, damped; the scroll term decays on its own when the page stops,
because `useSectionProgress` stops reporting and the difference goes to zero.

Depth is quantised into four bands and each band is stroked as one path, because
brightness and line width are both per-`stroke()` state and drawing honestly
would mean one call per star. Nine hundred stars therefore cost eight. Measured
in headless Chromium, which composites in software: 16.59 ms a frame mid-flight
against 16.59 ms at the footer with the field unsubscribed, no long frames
either way.

The rail matters more here than in the walkthrough. The walkthrough's beats are
captions; these contain their own controls, so with one beat on screen the rail
is the only way to reach the second and third demonstrations without scrolling.

**Audio** is entirely synthesised and there is exactly one way to hear any of
it: press Play on one of the three demonstrations. One `AudioContext`, built by
that click and by nothing else.

There was more, and what went is worth knowing. A pad ran behind the whole site
and a switch in the header brought it up — a drone that plays until you turn it
off is not atmosphere, it is a chore, and the switch's honest label would have
been "start a drone". Losing it took the interface voices with it, and not by
accident: with no switch, the only consent to audio is pressing Play, so a tick
fired by scrolling would be either inaudible or unasked for. Both argue for
deleting it, and it is deleted rather than parked behind a flag.

## What this project is, and what is unusual about it

A marketing page for a product that does not exist, built so that everything
behind the marketing is real. That inversion is the whole idea: the hardware is
invented and says so in the footer, while the rendering, the asset pipeline and
the memory accounting are not.

Three constraints were fixed before a line was written, and they turned out to
be the reason there is anything interesting here at all.

**No paid services, for the author or for a visitor.** No CDN with a bill, no
model API, no analytics vendor, no font subscription.

**Nothing is downloaded that the visitor did not ask for.** Every section below
the fold is code-split; the audio system does not exist until somebody presses
Play; the mobile stream is a third the size of the desktop one and the choice is
made before the first byte.

**Every asset is generated from code.** No stock photography, no bought 3D
model, no HDRI, no texture files, no audio files. `npm run assets:all` rebuilds
the 240-frame product render, both video streams, the PCB and die textures, the
X-ray pair and the noise tile from nothing, in about four minutes.

The third constraint is the one that paid off. A page that cannot buy its
visuals has to earn them, and the pipeline that produces them ends up being the
substance rather than the scaffolding. It also makes the repository honest:
clone it, run one command, and every pixel is reproducible.

### The things worth looking at

**A video used as a frame sequence.** The walkthrough is 240 pre-rendered
frames scrubbed against scroll. Conventional wisdom says video cannot be
scrubbed — and that is true of the `<video>` element, where `currentTime` is a
*request* to seek that the decoder answers whenever it likes. It is not true of
video. `VideoDecoder` takes chunks and returns frames in order, so the same 240
pictures cost 3.87 MB with inter-frame prediction against 9.95 MB as WebP
stills. The stills remain as the fallback, and a test deletes `VideoDecoder` to
prove that path still draws.

**No container.** MP4 would mean shipping a demuxer — mp4box.js is ~60 KB
gzipped. IVF is a 32-byte file header and twelve bytes per frame: thirty lines
of `DataView` and no dependency. Keyframe flags are read out of VP9's own
uncompressed header, so the file describes itself.

**Alpha, which video does not have.** Colour and matte are packed side by side
in one frame with a black gutter between them, because 4:2:0 chroma is shared
across two pixels and without the gutter the seam bleeds. They are recombined in
a WebGL2 shader inside the worker with no readback, and what comes out is an
ordinary `ImageBitmap` — so the cache, the byte budget and the draw path never
learn any of it happened.

**A scheduler that measures itself.** The player learns two things about the
machine it is on: how many frames a second the whole chain delivers, and how
long one round trip takes. It samples the timeline at a stride matching the
first and aims each request `speed × latency` frames ahead of the playhead, so
the frame lands *at* the scroll rather than behind it. Neither can be a constant:
the same build composites a frame in 0.1 ms on a discrete GPU and 32 ms on a
software rasteriser.

**Two pinned sections and no scroll plugin.** Both are a tall section, one
`position: sticky` child, and progress from a single `getBoundingClientRect` per
frame. That is about 30 KB of ScrollTrigger, a pin-spacer element and a class of
refresh bugs avoided, for roughly forty lines.

**Sound with no audio files.** Three demonstrations built from oscillators,
filters and a generated noise buffer — a log sweep, brown noise with the
suppression engaging mid-clip, and a panned orbit. The meter reads an
`AnalyserNode` tapped off the demos' own output stage, which is also how a
headless browser with no audio hardware can be asked whether a sound was really
made.

**Budgets that fail the build.** Eleven of them, in one file read by both the
gate and the page that quotes them — because those two disagreed once, and a
numbers page that drifts is worse than no numbers.

## Problems, and what they cost

Every entry here was found by measuring rather than by looking, and most of them
were invisible until the right number was taken. They are in the order they were
hit.

### The scrub that could not keep up

The report was "scroll the first section fast and the video skips twenty
frames". It did. The canvas covered 24 frames while the playhead crossed 239 —
a following ratio of **0.10**.

Three causes, none of them the obvious one.

A frame requested at N arrives `latency` later, by which point the scroll is at
N + speed × latency. On a software rasteriser that is sixty frames, against a
search range of twelve, so the canvas had nothing to show and froze. The fix was
to measure round-trip time as a *time* rather than as a distance in frames: a
distance is only true at one scroll speed, so it has to be relearnt exactly when
it is needed and has not converged.

Scrolling back up was the expensive direction. A frame decodes only from the
keyframe at or before it, so a reverse scrub asks for a descending ladder with
every rung behind the decode head — and serving the nearest rung first leaves
the next one behind the *new* head as well, costing a decoder reset per frame.
Going to the bottom of the ladder instead turns the whole thing into one rewind
and one forward sweep. Largest gap: 128–144 down to 42–80.

And `postMessage` is FIFO, so a window sent *after* the requests it authorises
loses them. The worker measured each request against a window it had a tick ago
and silently dropped the ones that had just come into range; the player counted
those as outstanding and never re-asked. Measured as the playhead sitting on
frame 163 with the canvas showing 149 and 27 requests pending, permanently.

Following ratio now **1.00–1.08**, and it is the figure the perf suite asserts
on precisely because it does not simply get worse on a slower machine.

### 190 MB of bitmaps

A guarded cache window bigger than the byte ceiling makes the ceiling
decorative. `BitmapLRU` stopped evicting once everything left was guarded, so at
1440² — 7.91 MB a frame, 29 in the window — it sat at 189.8 MB against a stated
160. The guard still beats the count limit and no longer beats the byte limit,
and the player sizes its window from what the budget affords.

Related, and the reason it went unnoticed: **a frame count is not a memory
budget.** The same 24 frames are 39 MB at 640² and 199 MB at 1440².

### A `subarray` that pinned 181 MB

`IvfReader` concatenated each network chunk onto a growing accumulator and
handed out views into it — so every frame kept its whole accumulator alive. 181
MB retained and 359 MB copied for a 3.87 MB stream, on the worker thread, during
the hero. It now copies each frame once into a buffer of its own size, and its
queue uses a head pointer rather than `shift()`, because shifting is O(n) in
queue length and the queue is longest exactly when the chunks are smallest.

### The blur nobody asked for

Reported as "there is a strange blur when I step through the video slowly".
There was. The draw kept the playhead's fractional position and cross-faded the
two frames it sat between.

Measured: the walkthrough turns 360° across the 72 frames of its rotate phase —
5° a frame, PSNR 20.7 dB between neighbours — so the blend read as a double
exposure, with the mic holes, the indicator and the port ring visibly doubled.
Worse at rest than in motion, because the damping settles on an arbitrary
fraction and the ghost then stays put forever.

It was also buying nothing. At 40px wheel steps the playhead crosses about 2.8
frames, so nearly every step lands on a different frame anyway: **58 distinct
pictures across 60 steps without the blend, 59 with**. The 87-against-48 figure
that had justified it compared the *video* against the *still fallback*, which
has half the frames — it was never a measurement of the blend at all.

### Two paragraphs at once

Reported as "the text goes weird when I scroll slowly". The acoustics beats
cross-wiped: beat N's exit and beat N+1's entrance ran over exactly the same
stretch of scroll, about 36svh, in which half of one paragraph sat above half of
the next and neither could be read. Stopping anywhere in it was guaranteed.

The fix is not a shorter transition, it is a gap. Each beat now owns a disjoint
window with empty scroll either side. That leaves a stretch with nothing on it,
which in the old design would have read as a broken page — and is the reason the
section became a flight between three stations with a starfield running at its
fastest exactly where the copy is absent.

`tests/unit/stations.test.ts` checks the invariant at a thousand scroll
positions in a millisecond, which is the argument for putting the arithmetic in
a module of its own: forty browser positions at three seconds each still only
samples forty.

### "One scroll and the card is just there"

Two causes, and the second one mattered more.

The approach owned a fifth of a station — 15svh, a wheel notch and a half from
parked to arrived. It now gets roughly twice the scroll the retreat does.

But length alone would not have fixed it. The stage ran on `easeInOutQuart`,
which parks near 0 and near 1 and crosses the middle at four times the average
rate, so a scroll-driven approach on that curve reads as *nothing, snap,
nothing* however much scroll it is handed. `smoothstep` is nearly linear through
the middle, so a notch of wheel buys a proportional step closer.

### The expensive thing was not the suspected thing

The 3D acoustics stage looked free. It was measured with the scroll *parked*,
which could not have found anything — blending and rasterisation only happen
while something is changing.

Measured properly (a fixed scroll rate, against a control scrolling the same
section where nothing moves, A/B interleaved in one session because the machine
drifts by more than the effect):

    translucent card, approach   19.90 ms/frame, 24 long frames
    control, same scroll rate    16.69 ms/frame,  1 long frame
    opaque card, approach        16.62 ms/frame,  0 long frames

The suspicion was rasterisation, since a scale change forces a layer to re-raster
to keep text sharp. Stepping the scale to cut those moved the figure from 19.90
ms to 19.90 ms, and the step was removed again rather than kept as machinery
that earns nothing. What cost was blending, and the bill follows the card's
*area* — which is exactly what coming forward increases. The fade now belongs to
the parking spot rather than to the journey.

### An audio graph built for silence

Interface voices called `ensureAudio()`, so scrolling past the scanner
constructed an `AudioContext` and a device handle. Nothing was audible, because
the master gain sat at zero until somebody switched sound on — which is exactly
why it survived: an entire audio system created for silence, on a page that
promises it stays off until asked.

### A trap file that was wrong

An entry here claimed `filter` breaks `position: sticky`. It was written from
general knowledge rather than from a measurement, and it is false. Probed in the
target browser:

    filter: blur()             STICKS
    will-change: transform     STICKS
    transform: translateZ(0)   STICKS
    contain: paint             STICKS
    overflow: hidden           BROKEN
    overflow-x: hidden         BROKEN
    overflow: clip             STICKS

`transform`, `filter` and `will-change` create a containing block for *fixed*
descendants; sticky is not fixed. A false entry in a traps file is worse than a
missing one, because it is trusted.

### Four loops with no end

Four separate sections were written with an animation loop that never stopped —
the scanner sweep, the configurator spin, the walkthrough playhead, the spectrum
meter. Every one of them kept drawing at the display's refresh rate for the rest
of the session, several screens up the page, in a background tab. Measured parked
at the footer with every section mounted and none visible: **720 `clearRect` and
720 `getBoundingClientRect` in three seconds, against 0 after.**

Writing the same bug four times is what moved the gate into
`onFrameWhileVisible` rather than leaving it to be remembered at each call site.

### Tests that lied

Worth their own entry, because more time went into these than into some of the
features.

*Fixed sleeps in canvas tests are a flake generator.* Sleeps tuned on an idle
machine fail under a parallel run. `scrubTo` waits for the frame to change **and
then settle** — waiting only for stability exits immediately, because right
after a scroll the canvas still holds the previous frame and is briefly
perfectly stable.

*A performance test must not share the machine.* Run beside the rest of the
suite, the perf suite reported a largest gap of 169 where it reports 42–80
alone. That is why it has its own config at one worker, and why it asserts on
the following ratio — the one figure that does not simply degrade on slow
hardware — while merely logging granularity, which does.

*Two tests were failing on their own budget, not on their claim.* Both reported
as page faults: one as "the walkthrough never drew a frame", one as
`frame.evaluate: Test timeout`. Both were the default 30 s test timeout expiring
around a cold boot and an axe pass over the longest document on the site.
Raising the *poll* on the first achieved nothing, which is the tell.

*Headless Chromium composites in software, and it is roughly 300× slower.*
Profiling headless and optimising for what you find is optimising for a machine
nobody uses. Check the renderer string before believing a number — and note it
cuts both ways, which is why the CI budgets are looser than the figures a real
browser reports.

### Internals that looked like stickers

The complaint was that the exploded view looked cheap, and the first instinct
was the obvious one: these are primitives with pictures on them, so the fix
must be geometry — a board with parts standing off it, a package with a lead
frame, a driver with a basket. That instinct was wrong, or at least premature.

Reading the material setup first turned up something better. Every internal
part was a flat base colour with its *entire* texture on `emissiveMap` and
nothing on `map`, `roughnessMap`, `metalnessMap` or `normalMap`. Emissive is
self-lit. It ignores every light in the scene, takes no shading across a form,
throws no specular and carries no depth — so three good drawings were being
displayed rather than lit, which is precisely what "sticker" means. The whole
board also had one uniform roughness of 0.62, so copper, mask and silkscreen
had identical gloss, which happens on no real board ever made.

The generators now paint three canvases from one set of drawing calls — albedo,
roughness and metalness packed into G and B of one texture the way glTF does
it, and a height map that becomes a normal map through a Sobel pass. Painting
them in lockstep is not tidiness: a roughness map drawn in a second pass drifts
from the albedo by a pixel here and there, and a pad whose gloss is half a pixel
off its colour looks *wrong* in a way that is very hard to trace back to the
texture.

Two things then had to follow the change rather than lead it. The emissive
levels the timeline drives are now a twentieth of what they were, because they
were standing in for lighting and are now a stylisation on top of it. And the
driver had to be turned: its cone faces the bezel, which is the ear side, which
is away from the camera — so built correctly, the one surface worth looking at
was the one nobody would ever see. `addPart` takes an optional rotation applied
in step with the explode, which is what exploded views are for.

### 4.5 seconds hiding in the wrong line

Generating the six texture sets took 4.6 s, which is fine at prerender time and
not fine in the configurator, where the same module runs on the visitor's main
thread. Timing each generator put 4604 ms of it in the board and 245 ms in the
other five. Timing each *section* of the board put 4514 ms in the Sobel pass and
about 3 ms in every drawing call that fed it.

That reading was a lie, and the shape of the lie is the useful part: canvas
drawing is deferred. The paint calls queue, and the first `getImageData` pays
for replaying the lot plus a synchronous readback off the GPU. The profile
blames whichever line happens to touch the pixels.

The fix is `getContext("2d", { willReadFrequently: true })` on the canvases that
get read back — 4604 ms to 58 ms, one argument. The confirmation came free: a
leftover probe still reading an unhinted canvas took 6280 ms for the same work.

Two guards against believing this kind of number again. To attribute cost
inside a generator, force a flush at each mark, or you are timing when the
queue drained. And of the three canvases per part, only the height map is ever
read into JS — the other two go to `texImage2D` and never come back — so the
hint belongs on exactly one of them.

What it settles at, measured in a real browser on a discrete GPU rather than in
headless: 195 ms for all six sets — board 51, die 40, brushed 32, cell 27,
driver 26, grille 20. That is one blocking chunk on the visitor's main thread,
and it is not free. It is also paid once, on mounting a lazy section that
already fetches three.js and builds an environment map, and it is the whole
price of generating six complete PBR material sets in the browser instead of
downloading them. The Sobel passes stay at 512² for that reason: a normal map
describes which way a surface leans, which is low-frequency, and matching the
1024² albedo would quadruple the only part of this that is pure main-thread JS
for a difference invisible at the size these parts are drawn.

### Shell quoting, four times

Twice a heredoc broke on backticks and quotes while writing TypeScript. The
third time was worse: a `perl -0pi -e` replacement ended with a dollar sign
immediately before a backtick, which Perl reads as `$PREMATCH`, and it pasted
every preceding line of this file back into itself — duplicating the document
end to end. The fourth was a `node -e` patch script whose replacement text
carried literal `\n` escapes outside any string, which left the shell hunting a
closing backtick that was never coming. Prose and code go through the editor,
not through a shell one-liner.

## What was removed, and why

Deletions are decisions too, and these are the ones that would otherwise look
like something went missing.

**A power model.** A battery capacity, per-mode draw figures and a runtime
integrator feeding an interactive tile, a generated PDF and a scripted answer.
Internally consistent, and still invented — and an invented number presented as
a measurement is the one thing a portfolio piece cannot afford.

**An ambient pad and a sound switch.** A drone that plays until you turn it off
is not atmosphere, it is a chore, and the switch's honest label would have been
"start a drone". Losing it took the interface voices with it: with no switch,
the only consent to audio is pressing Play, so a tick fired by scrolling would
be either inaudible or unasked for.

**A dev inspector and a command palette.** Two switches in the footer that made
the page a toy for the person who built it. What the inspector measured is still
measured — `?debug=1` publishes the same object, and `tests/perf` reads it.

**Coordinates beside the cursor.** A number that changes as fast as your hand
moves and means nothing to anybody reading it, printed next to the pointer
because it looks like instrumentation. Set dressing pretending to be telemetry,
on a site that has real telemetry elsewhere. The crosshair went with it — aiming
arms and a ranging circle imply a precision the scanner does not have.

**An electric cyan accent.** The colour every hardware concept page reaches for,
and most of the reason they all look alike. The accent is warm bone now, with no
hue at all, and the change went all the way down: the PCB traces, the die
floorplan and the core's emissive material were regenerated, because a bone
interface over a cyan product reads as a mistake rather than as a choice.
