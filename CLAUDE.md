# AURA ONE

A product page for hardware that does not exist, built as a portfolio piece
about scroll-driven canvas rendering, procedural asset generation and
memory discipline.

**The founding constraint: every asset is generated from code.** No stock
photography, no purchased 3D model, no HDRI, no texture files, no audio files,
no paid API keys — for the author or for anyone opening the page. If a change
would introduce a binary asset that cannot be regenerated by
`npm run assets:all`, that is a design decision worth stopping to discuss, not a
detail.

Long-form reasoning lives at `src/app/engineering/page.tsx`, rendered for
visitors at `/engineering`. `README.md` is the contributor-facing version. This
file is the working knowledge that is expensive to re-derive.

---

## Commands

```bash
npm run dev              # Next 16 dev server, Turbopack
npm run verify           # typecheck + lint + 25 unit tests — run before every commit
npm run build            # production build
npm run audit:budget     # asset + JS budget gate; needs a build first
npm run test:e2e         # 46 Playwright tests, desktop + mobile projects (~8 min)
npm run test:a11y        # 12 axe / keyboard / reduced-motion tests
npm run test:perf        # scrub continuity, own config, one worker (~30 s)
npm run assets:all       # regenerate every asset from primitives (~4 min; needs ffmpeg)
node scripts/shoot.mjs   # screenshot the stage at five scroll positions
```

All three Playwright suites reuse a running server when there is one and
otherwise build and start their own, and all three need `public/seq/` to exist —
it is committed, so a fresh clone works without a render.

`test:perf` has its own config (`playwright.perf.config.ts`) at one worker. It
drives the page with `?debug=1`, which is the only thing that puts the live
telemetry object on `window`; a normal visit pays one string comparison at boot
and gets nothing else.

## Hard rules

These are the ones that cause silent breakage rather than an error.

1. **Nothing that changes per frame goes through React state.** Per-frame values
   are written straight to `style` on refs, or to the mutable `telemetry` object
   in `src/store/transient.ts`. A full scrub of the stage causes zero
   re-renders; keep it that way. Zustand is for discrete state only — the
   material, the audio toggle, the story phase (which changes three times in
   total).

2. **There is exactly one animation loop**, `src/lib/scroll/rafBus.ts`. Never
   call `requestAnimationFrame` directly. Subscribers run in ascending priority:
   `INPUT` (0) may read layout, `RENDER` (100) may only write, `MEASURE` (200)
   observes the finished frame. Reading layout after a write in the same frame
   forces a synchronous reflow.

3. **`ImageBitmap` must be `close()`d.** Its memory lives outside the JS heap and
   GC will not reclaim it. `BitmapLRU` owns this; the unit tests assert on
   `close()` calls rather than on cache size, because skipping the call still
   *works* — it just leaks until the tab dies.

4. **Frames decode to the size they will be drawn**, not the size they were
   encoded. A bitmap costs the same whether or not the detail is visible.

5. **The shell renders neutral grey in the baked frames.** The walkthrough is
   a frame sequence, so a colour baked into the render means re-rendering all
   240 per variant. The live configurator overrides it through
   `setFinish`; the no-WebGL fallback composites it at draw time.

   And: **the two frame sources must stay interchangeable.** `video.worker.ts`
   and `decoder.worker.ts` speak one protocol and both return `ImageBitmap`s
   at drawn size. Anything that makes the player branch on which is running has
   put the abstraction back where it started.

6. **Anything that animates on a loop is gated on visibility.** Use
   `onFrameWhileVisible` from `src/lib/scroll/onScreen.ts`, never `onFrame`
   directly, for anything with no natural end — an idle spin, a sweep, a
   damped playhead. This has been the same bug four times. Measured parked at
   the footer with every section mounted and none visible: 720 `clearRect`
   and 720 `getBoundingClientRect` in three seconds, against 0 after.

7. **New below-the-fold sections are code-split.** Client wrapper +
   `next/dynamic({ ssr: false })` + `LazySection`, following
   `src/components/xray/XraySectionLazy.tsx`. Pass `LazySection` the section's
   `id` so the anchor exists before the section mounts.

8. **Numbers appear in one place.** The spec table and the encoder-written
   manifest are what the page and the engineering notes read. Nothing on this
   site may quote a frame count, a file size or a figure the build disagrees
   with — a spec sheet contradicting the paragraph beside it is the worst
   failure this project can have.

## Traps

Each of these cost real time. They are all still live.

**`tailwind-merge` and the custom type scale.** It assumes any unrecognised
`text-*` class is a colour, so `text-display text-ink` reads as a conflict and
the font size is silently dropped — a headline at 16px with no error anywhere.
`cn()` in `src/lib/utils.ts` registers the scale. Any new `@theme` key sharing a
prefix with a built-in group needs the same treatment.

**`globalCompositeOperation: "color"` cannot darken.** It takes hue and
saturation from the source and *luminosity from the backdrop*. Filling a bright
chrome render with near-black gives bright chrome and an invisible hue shift.
Lightness comes from `Material.exposure`, authored from the OKLab lightness of
the tint. See `src/lib/canvas/tint.ts`.

**Assigning to `canvas.width` resets the whole 2D context state.** Smoothing,
alpha, transform, composite mode — all of it, every time, including when you
assign the same value it already had. Anything configured once in a constructor
survives exactly until the first resize, and the first resize happens during
boot. `imageSmoothingQuality` is re-applied inside `resize()` for that reason,
and it is not decoration: the master is 1440 square and a 1440p panel at dpr 2
draws the artwork at 2477 device pixels, so an upsampling filter runs on every
frame whether or not anyone chose one.

**The decode size quantises with `ceil`, and both halves of that matter.** It
keeps the decode at or above the drawn size so the 2D canvas only ever scales
*down*, and it holds the whole hero-to-story framing sweep inside a single
160px step — at dpr 1 on a 1080p panel the drawn square runs 817 to 929 px, and
`ceil` calls both of those 960 where `round` would call them 800 and 960 and
invalidate the entire cache halfway through the opening animation.

**A frame count is not a memory budget.** The same 24 frames are 39 MB decoded
at 640² and 199 MB at 1440². `BitmapLRU` takes both a count and a byte ceiling.

**A `VideoFrame` pins a decoder buffer**, the same way an `ImageBitmap` pins
heap-external memory. `onFrame` closes in a `finally` on every path,
including the ones that return early — hold a handful and the decoder stalls
waiting on its own pool, silently.

**The video scheduler needs to know what is already in flight.** Without it,
"you asked for that and it is coming" is indistinguishable from "that is behind
the head, rewind", and it picks the second. The first version reset the decoder
on every network chunk and produced not one frame, without ever erroring —
resetting a decoder is perfectly legal. `inFlight` in `video.worker.ts` is
that distinction.

**A decoder's queue is latency, not buffer.** It is a FIFO: a frame requested
now comes out after everything already queued has. Depth measured in frames
hides that completely — twenty-four frames is 40 ms of latency where a
composite costs 1.65 ms and 900 ms where it costs 38, and both are real
machines. The depth is derived from the measured composite cost
(`TARGET_QUEUE_MS`), not chosen.

**Never rewind while the sweep still has work ahead of it.** The decode head is
deliberately ahead of the playhead, so the frame on screen is usually *behind*
the head, and chasing it means `reset()` — which drops everything in flight.
Then the playhead moves and it happens again. Measured as half a second in
which the decoder ran flat out and delivered three frames. `pickTarget` takes
anything ahead first and only rewinds when the sweep has genuinely run out.

**A request has to aim where the playhead is going.** A frame asked for at N
arrives `latency` later, by which point the scroll is at N + speed x latency —
sixty frames on a software rasteriser against a `nearest()` search range of
twelve, so the canvas had nothing to show and froze. The player measures
round-trip time as a *time*, not as a distance in frames: a distance is only
true at one scroll speed, so it has to be relearnt exactly when it is needed
and has not converged. A time is a property of the machine, learnt during
ordinary scrolling and already right when a flick starts.

**`nearest()` is asymmetric about the direction of travel**, not about the
index. Against the travel it covers the measured lag; with the travel it must
not, because the player aims ahead deliberately and the frames arriving early
are frames the scroll has not reached — a symmetric search showed frame 220
while the playhead was at 162. Which side counts as "stale" flips when the
scroll reverses, and hard-coding it towards lower indices was right going down
the page and exactly backwards coming up.

**Scrolling back up is the expensive direction.** A frame decodes only from the
keyframe at or before it, so a reverse scrub asks for a descending ladder with
every rung behind the decode head. Serving the nearest rung first leaves the
next one behind the *new* head as well, and every frame costs its own reset:
`pickTarget` goes to the bottom of the ladder instead, which turns the whole
ladder into one rewind and one forward sweep. Frames then arrive in the opposite
order to the one the playhead wants, which does not matter — they land in the
cache either way. Removing this took the largest gap from 128–144 to 42–80.

**postMessage is FIFO, so a window sent after the requests it authorises loses
them.** The worker measures each request against the window it had a tick ago
and silently drops the ones that have just come into range; the player counts
those as outstanding and never re-asks. Measured as the playhead sitting on
frame 163 with the canvas showing 149 and 27 requests pending, permanently.
`prefetch` announces first, then asks.

**A `subarray` pins the buffer it was cut from.** `IvfReader` used to
concatenate each network chunk onto a growing accumulator and hand out views
into it, so every frame kept its whole accumulator alive — 181 MB retained and
359 MB copied for a 3.34 MB stream, on the worker thread, during the hero. It
now copies each frame once into a buffer of its own size. Its queue uses a head
pointer rather than `shift()`: shifting is O(n) in queue length and the queue
is longest exactly when the chunks are smallest.

**A guarded cache window bigger than the byte ceiling makes the ceiling
decorative.** `BitmapLRU` used to stop evicting once everything left was
guarded, so at 1440² — 7.91 MB a frame, 29 in the window — it sat at 189.8 MB
against a stated 160. The guard still beats the *count* limit and no longer
beats the byte limit, and the player sizes its window from what the budget
affords.

**`background-position` is not a compositable property**, and neither is
anything else you might reach for to move a texture. Animating it repaints the
element every step; `will-change: background-position` only gives it a layer to
repaint in. `mix-blend-mode` is worse in a different way — it forces the
compositor to read the backdrop, and the grain sits directly over the stage
canvas. Move an oversized child by `transform` instead, and compensate the
overhang in `background-position` or the tile lands on different pixels.

**What breaks `position: sticky` is `overflow`, and only `overflow`.**
Measured in the target browser rather than assumed, because this entry
previously claimed `filter` was the culprit and that is simply false:

    plain (control)            STICKS
    filter: blur()             STICKS
    will-change: transform     STICKS
    transform: translateZ(0)   STICKS
    contain: paint             STICKS
    overflow: hidden           BROKEN
    overflow-x: hidden         BROKEN
    overflow: clip             STICKS

`transform`, `filter` and `will-change` create a containing block for *fixed*
descendants — sticky is not fixed, and it positions against the nearest
scrollport. `overflow: hidden` makes an ancestor into that scrollport, which is
why it is the one that bites; `overflow-x: hidden` bites for the same reason,
because it computes `overflow-y` to `auto`. `overflow: clip` does not create a
scroll container and is the safe way to clip around something pinned.

Both pinned sections put `overflow-hidden` on the sticky element *itself*, which
is fine — it is ancestors that matter.

**A percentage translation is relative to the element, not to what clips it.**
The masked wipe in the acoustics section moves each block by 115% — of its own
height, which for a one-line title inside a two-line window leaves it sitting in
the window, in full view, having "left". Every mover is stretched to fill its
window (`h-full`) and every window has a fixed height, so the two agree.

**Paged beats have to align slot for slot.** Centred independently, beats of
unequal height put their titles at different heights, and the outgoing and
incoming ones cross at an offset — which reads as two paragraphs colliding
rather than one slot changing its contents. Align from a fixed top and give the
variable-height blocks a fixed height.

**Never put a focusable control inside an `overflow: hidden` window.** The clip
takes the focus ring with it, and the focus ring is the only feedback a keyboard
user has about where they are. In the acoustics beats the Play button sits
outside the masks and moves on transform and opacity instead.

**A blur radius has to be quantised.** `opacity` and `transform` are compositor
properties and cost nothing per frame; `filter: blur()` re-rasterises the layer
at layer size on every distinct radius. `SectionHandoff` steps the radius so a
whole transition costs four or five rasterisations rather than one per frame,
which is the same answer `.noise-field` reached with `steps(8)`. And at the ends
the filter is *removed*, not set to `blur(0px)` — a zero radius still promotes
the element and still runs the pass.

**An entrance and an exit across one boundary must be complements.** For
adjacent sections the incoming top edge and the outgoing bottom edge are the
same edge, so thresholds measured from the viewport top make `enter + exit`
sum to exactly 1 and the boundary cross-dissolves. Measuring each from the
nearest viewport edge instead looks equivalent and is not: measured across the
boundary, the incoming section was fully arrived before the outgoing one had
begun to leave.

**Interface sounds must never construct the AudioContext.** `tick()` and
`sweepDown()` used to call `ensureAudio()`, so scrolling past the scanner built
an audio graph — the lens firing `lock()` at a hotspot is a scroll-driven event,
not a request for sound. Nothing was audible, because the master gain is zero
until somebody switches sound on, and that is exactly why it survived: a graph
and a device handle created for silence. They take the context only if one
already exists; `ensureAudio()` belongs to the deliberate switch-on path.

**`getByRole("button", { name: /Sound/ })` is a substring, not a name.** It
matched the audio toggle until the acoustics section added "Play — Sound keeps
its address.", and then failed as a strict-mode violation in two suites at once.
Anchor role-name regexes.

**`will-change` is a promise, not a hint you can leave on.** It holds a
compositor layer for as long as it is set. The hero copy and the four captions
are full-viewport elements; clear it in the same write that sets
`visibility: hidden`.

**Lenis owns the scroll position, so tests must not jump.** A programmatic
`window.scrollTo` gets pulled back towards Lenis's own target, and a test that
jumps is measuring somewhere other than where it thinks it is. That produced a
very convincing screenshot of the wrong frame. Drive with `mouse.wheel`, and
converge rather than aiming once — the inertial tail overshoots a single
impulse.

**The e2e suite runs two workers on purpose.** Each one decodes a 2896x1440 VP9
stream or renders three.js through software WebGL while reading pixels back. One
worker per core starves them, and starvation looks exactly like the regressions
the tests exist to catch.

**A performance test must not share the machine.** `tests/perf` has its own
config at one worker for that reason: run beside the rest of the suite it
reported a largest gap of 169, where alone it reports 42 to 80 on the desktop
stream and 21 to 28 on the mobile one. For the same reason it asserts on the
fraction of the playhead's journey the picture covered — the one figure here
that does not simply get worse on a slower machine — and merely *logs*
granularity, which does.

**Headless Chromium composites in software, and it is 300x slower.** WebGL in
the worker runs on SwiftShader: the packed-frame texture upload costs 32 ms
there against 0.1 ms on a discrete GPU. Profiling headless and optimising for
what you find is optimising for a machine nobody uses — check the renderer
string before believing a number. It cuts both ways: the same gap is why the
CI budgets are looser than the figures a real browser reports.

**Boot progress must be measured, not counted.** A resize bumps the decoder's
generation and the worker discards everything in flight, so counting replies
leaves the counter permanently short and the preloader never releases the page.
It only reproduces where layout settles late — every mobile test failed, desktop
never did. There is also a hard 12 s timeout, because an overlay that blocks
scrolling must always let go.

**Fixed `waitForTimeout` in canvas tests is a flake generator.** Sleeps tuned on
an idle machine fail under a parallel run. Poll for the actual state: `scrubTo`
in `tests/e2e/stage.spec.ts` waits for the frame to *change and then settle*
(waiting only for stability exits immediately, because right after a scroll the
canvas still holds the previous frame and is briefly perfectly stable).

**Satori needs explicit `display: flex`** on any element with more than one
child, and JSX makes `{X}.` two children. `src/app/opengraph-image.tsx` uses
template literals to keep text nodes single.

**ESLint blocks `setState` inside effects.** For platform capabilities that never
change, use `useClientValue` (`src/lib/useClientValue.ts`), which wraps
`useSyncExternalStore`. Never write a ref during render either — construct
lazily inside a callback instead.

**A `listbox` may contain only `option` and `group`.** The obvious
`ul > li > button role="option"` nests three invalid ARIA relationships. The
palette is the combobox pattern: the input keeps focus,
`aria-activedescendant` points at the active option.

**`playwright.config.ts` needs `testMatch`.** `testDir: "tests"` otherwise picks
up `tests/unit` and fails on the first vitest import. It also has to leave
`perf/**` out, or the performance suite runs two-wide with everything else and
measures the neighbours; `playwright.perf.config.ts` spreads the base config and
overrides only what runs and how much runs beside it.

## How the pieces work

**Stage.** Hero and scrollytelling share one canvas, so there is no seam to
cross-fade between "product at rest" and "product rotating". The pinned section
is `position: sticky` — there is no GSAP and no ScrollTrigger — and progress is
one `getBoundingClientRect` per frame during the INPUT phase. Camera framing is
a per-tier table of hero and story poses: desktop moves the product sideways to
make room for copy beside it, mobile moves it up because there is no beside.

**Two frame sources, one protocol.** `video.worker.ts` drives `VideoDecoder`
over a VP9 IVF stream; `decoder.worker.ts` fetches WebP stills. Both return
`ImageBitmap`s at drawn size, so the LRU, the byte budget and the draw path are
identical either way. The worker reports `unsupported` and the player swaps —
the probe is async and the answer is only needed inside the worker. Which one
won is on the canvas as `data-source`, because production strips
`window.__player` and the fallback is invisible when it works *and* when it
breaks.

**Why a video, given the whole player exists because video cannot be scrubbed.**
That is true of the `<video>` element, not of video: `currentTime` is a
request to seek, `VideoDecoder` is not. Inter-frame prediction then costs
3.34 MB where the same 240 pictures cost 9.09 MB as stills.

**Seeking.** A frame decodes only from the keyframe at or before it, so a
backwards jump costs up to one GOP (16). Frames passed on the way are
composited if they were wanted and dropped if not — one decode either way.

**Scheduling.** Everything the player does about a fast scrub comes from two
measurements it takes of itself: delivery rate, in frames per second, and
round-trip latency, in seconds. Below the delivery rate it asks for every frame
and nothing changes. Above it, the timeline is sampled at a stride that matches
what can actually arrive, and each request aims `speed x latency` frames ahead
of the playhead so the frame lands *at* the scroll rather than behind it. Both
are properties of the machine rather than constants: the same build composites
a frame in 0.1 ms on a discrete GPU and 32 ms in software, and a number chosen
for either one is wrong on the other.

The visible consequence is that a slow machine draws fewer, wider-spaced
pictures and still follows the scroll end to end. That is the figure
`tests/perf` asserts on, and it was 0.10 before this — the canvas covered
twenty-four frames while the scroll crossed two hundred and thirty-nine.

**Whole frames only.** The draw used to keep the playhead's fractional position
and cross-fade the two frames it sat between. It was removed: the walkthrough
turns 360 degrees across the 72 frames of its rotate phase — 5 degrees a frame,
PSNR 20.7 dB between neighbours — so the blend read as a double exposure rather
than as travel, with the mic holes, the indicator and the port ring visibly
doubled. Worse at rest than in motion, because `damp()` settles on an arbitrary
fraction and the ghost then stays put forever.

It was also buying nothing. At 40px wheel steps the playhead crosses about 2.8
frames, so nearly every step lands on a different frame regardless: 58 distinct
pictures across 60 steps without it, 59 with. The 87-against-48 figure it was
justified by compared the *video* against the *still* fallback, which has half
the frames — it was never a measurement of the blend.

**Format split.** VP9 for the walkthrough, WebP for its fallback, AVIF for the
two X-Ray stills. AVIF is ~18% smaller per frame but decodes ~3× slower with
alpha, and a fast scrub decodes several frames per animation frame. Bytes are
one-time; decode is per-scrub.

**Scanner.** Two renders from an identical camera, stacked, with a circular
window into the lower one. The lens is a fixed-size element that is
*translated*, and the copy of the artwork inside it is translated by exactly the
opposite amount. Animating `mask-image` or `clip-path` position recomputes the
mask on the compositor's critical path every frame.

**Section hand-off.** Sections do not abut, they dissolve into one another:
`SectionHandoff` drives opacity and scale continuously and a stepped blur
alongside them, from each section's own edges. Blur is dropped on mobile and
under reduced motion, where opacity and scale carry it alone.

**Text entrance** is `Reveal`, on the shared frame bus. There is no GSAP here
and there is not going to be: it is ~40 KB gzip against 15 KB of first-load
headroom, and it brings its own ticker into a page whose ordering guarantees
depend on there being exactly one.

**Acoustics.** The only claim on the site made in sound, and it ships no audio
bytes — a sweep, brown noise with the suppression engaging mid-clip, and a
panned orbit, all built from oscillators and filters. The meter reads an
`AnalyserNode` tapped off the demos' own output stage rather than the master
bus, so it cannot twitch at the ambient bed. It draws its resting state once
and only subscribes to the frame loop while something is playing.

**The second pinned section.** On a wide viewport the acoustics section is
380svh with a sticky frame, paging through its three beats on a masked wipe —
the same sticky-plus-one-rect mechanism as the walkthrough, which is the whole
argument for not having taken a scroll plugin. On a narrow viewport, and under
reduced motion, it is an ordinary stacked list instead: `AcousticsPinned` and
`AcousticsFlat` are separate components because they are genuinely different
documents — one keeps a single beat in the tab order, the other holds all three
— and `useAcousticsDemo` owns everything that is not layout.

The rail matters more here than in the walkthrough. The walkthrough's beats are
captions; these contain their own controls, so with one beat on screen the rail
is the only way to reach the second and third demonstrations without scrolling.

**Audio** is entirely synthesised, ambient bed included. One `AudioContext`,
created on the first gesture. A hover tick can be pitched per element, which a
sample cannot do without shipping one per variant.

## Asset pipeline

```bash
npm run assets:all   # noise → prerender (~115 s) → encode (~25 s) → video (~90 s)
```

The encoded output is committed; the ~700 MB of master PNGs is not.
`assets:video` is the only step that needs **ffmpeg**.

**Swapping in a Blender render.** The seam is the output contract, not the
scene. Drop into `assets-src/out/` and run `npm run assets:encode`:

- `aura_0001.png` … `aura_0240.png` — exactly 240, square, PNG RGBA with a
  transparent background (`Film → Transparent`)
- `xray-outer.png`, `xray-inner.png` — 16:9, from an **identical camera**

Two constraints carry over: render the shell neutral grey, and keep the phase
boundaries (1–72 rotate, 73–168 explode, 169–216 push into the core, 217–240
reassemble). `src/data/story.ts` caption windows are asserted against them by a
unit test. If the X-Ray camera moves, regenerate `hotspots.json` with
`npm run assets:prerender` rather than editing it.

## Testing

The scrollytelling cannot be checked by asserting on the DOM — everything that
matters happens inside a canvas React never re-renders — so those tests read
pixels: coverage, frame fingerprints, mean luminance for the finish tests.

- `tests/unit/` — vitest. LRU eviction, `close()` and the byte ceiling; the
  IVF reader across four chunkings; caption timing; frame-rate-independent
  damping.
- `tests/e2e/` — Playwright, `desktop` and `mobile` projects.
- `tests/perf/` — scrub continuity under a fast flick, own config, one worker.
  Asserts on the fraction of the playhead's journey the picture covered and on
  where it lands when the scroll stops; logs granularity without asserting on
  it, because that one is a measure of the machine.
- `tests/e2e/acoustics.spec.ts` — that a demo actually builds a running graph,
  read off the meter rather than through a test-only probe, and that no
  `AudioContext` exists until one is asked for (counted by patching the
  constructor in an init script, because "the browser blocked us" and "we never
  tried" look identical from outside).
- `tests/a11y/` — axe on the chrome, on every lazy section once mounted, on the
  palette while open, on `/engineering`; plus the skip link, keyboard
  reachability and the reduced-motion path.

CI (`.github/workflows/ci.yml`) builds once and reuses it for all three
Playwright suites. There is no Lighthouse job: its stable categories are already covered by
axe and the budget gate, and a performance score from a shared runner flaps

consumers that must not disagree, and they did: the page advertised a 5.50 MB

## Conventions

- TypeScript strict, plus `noUncheckedIndexedAccess` and `verbatimModuleSyntax`
  (use `import type`).
- Comments explain *why*, especially where the obvious implementation is wrong.
  Several of the traps above are documented at their call site; keep that.
- Design tokens live only in `src/app/globals.css`. No raw hex outside it,
  except where satori cannot read CSS (`opengraph-image.tsx`, commented).
- All numbers rendered to the user carry `data-numeric` for tabular figures.
- Conventional Commits, and commit messages state what was found and fixed, not
  just what changed.

## Known items

- `src/data/author.ts` still holds placeholder GitHub and LinkedIn URLs.
- `assets-src/device/scene.mjs` is imported by the app through the `@device/*`
  alias and typed by a hand-written `scene.d.mts`. It stays plain ESM because
  the prerender harness serves it straight to headless Chromium through an
  import map; converting it to TypeScript would put a bundler back in the render
  path.
- The dev-only `window.__player` handle in `Stage.tsx` exists for
  `scripts/shoot.mjs` and devtools poking. It is stripped in production, which
  is why `?debug=1` exists separately: it publishes the live `telemetry` object
  as `window.__telemetry` in any build, and is what `tests/perf` measures
  through.
- `make-noise.mjs` asks the PNG palette for 8 greys and gets 4 — the quantiser
  merges what it judges indistinguishable at 3% opacity. `LEVELS` is a ceiling,
  not a result, and the script logs what it wrote rather than what it asked for.
